# Repository Guidelines

## Project Structure & Module Organization

Symlinkr is a small Go CLI organized as a single `main` package. `main.go` handles flags, modes, and summaries. `config.go` parses and validates `symlinkr.yaml`; `symlink.go` contains filesystem operations. Tests live beside the code in `main_test.go`. User-facing documentation and the example configuration are in `README.md` and `symlinkr.yaml.example`. Automation lives in `Taskfile.yml`, while CI and release workflows are under `.github/workflows/`.

## Build, Test & Development Commands

Use the pinned Go version from `go.mod` and Task for common workflows:

- `task run -- --config symlinkr.yaml --dry-run` runs the CLI safely.
- `task build` creates `dist/symlinkr` with version metadata.
- `task test` runs `go vet ./...` followed by `go test ./...`.
- `task lint` runs `golangci-lint run --timeout 3m`.
- `task security` checks dependencies with `govulncheck ./...`.
- `task all` runs formatting, linting, vetting, security checks, and tests.

Run `go test -race ./...` when changing filesystem traversal or shared state.

## Coding Style & Naming Conventions

Format Go files with `gofmt`; use tabs as generated by the formatter. Follow standard Go naming: exported identifiers use `PascalCase`, internal variables use `camelCase`, and tests use `TestFunctionScenario`. Keep filesystem logic small, explicit, and based on `filepath` helpers. Wrap operational errors with useful path context and update `Stats` consistently.

## Testing Guidelines

Use Go's standard `testing` package, `t.TempDir()`, and isolated filesystem fixtures. Cover successful operations, dry runs, missing paths, existing files, and ownership boundaries. Regression tests for removal must prove that managed links are removed while unrelated links, external targets, and directories remain untouched. No numeric coverage threshold is enforced.

## Commit & Pull Request Guidelines

Prefer short, imperative Conventional Commit messages such as `fix: remove only managed symlinks` or `docs: clarify recursive behavior`. Keep commits focused. Pull requests should explain What, Why, and Test; link the relevant issue with `Fixes #7` when applicable. Include CLI output for behavior changes and ensure CI passes before marking a draft ready.

## Recursive Removal Safety

- Remove recursive symlinks only when the current source tree contains the corresponding path and the destination symlink points to that exact source path.
- If a source file was deleted or moved, preserve its dangling destination symlink. This is intentional: Symlinkr is stateless and cannot safely confirm ownership without the source.
- Preserve unrelated symlinks and destination directories. Do not infer ownership by scanning the destination tree.
